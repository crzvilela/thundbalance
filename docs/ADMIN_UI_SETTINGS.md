# Personalising the admin panel

The studio's admin can rename, reorder and hide what it does not use from "Personalizar panel" (the button at the end of the side menu, only for the main admin): the **menu** areas, the **Overview** cards and the **title and subtitle of each page**. There is ONE configuration for the whole studio, stored in a single row of `admin_ui_settings` (`key = 'panel'`, `{"menu", "overview", "pages", "version"}`); a name is one text for both languages, and where nothing is customised the original text (ES / EN) is shown, so with no configuration the panel is exactly the original one. `GET /admin/ui-settings` returns it (or `{}`), `PUT` validates and saves it (it must send the `version` it loaded, otherwise 409; the first save is version 0), `DELETE` removes the row ("Restablecer todo"); all three are admin only. Only keys of a closed registry can be customised and nothing else is stored: names up to 30 characters, subtitles up to 120, no `<` or `>` and no control characters, at most 8 KB, the Overview item and the "Personalizar panel" button can never be hidden and at least 3 menu areas always stay visible (the server refuses it with 422 and the editor warns). The panel never depends on it: the frontend loads it once, never waits for it, and if the request fails or the answer is not valid it uses the original values; a key that is missing from a saved configuration (for example a new area added later) simply appears at the end with its original name. While editing, the changes are applied live to the menu and the Overview without saving; everything that can be dragged also has up / down buttons and works with the keyboard and on a phone.

## Editable keys

| Group | Keys |
|---|---|
| Menu (`menu`) | `overview` (protected), `requests`, `trials`, `messages`, `sent-messages`, `clients`, `calendar`, `schedule`, `trainers`, `plans`, `videos`, `landing`, `customize` (the editor button: protected, always last, can be renamed) |
| Overview cards (`overview`) | `stat_clients`, `stat_sessions`, `stat_pending`, `week`, `pending`, `business`, `upcoming`, `quick` |
| Pages (`pages`, title + subtitle) | `overview`, `requests`, `trials`, `messages`, `sent-messages`, `clients`, `calendar`, `schedule`, `trainers`, `plans`, `videos` |

## Adding a new area (or card, or page)

1. **Frontend registry** `src/admin/uiRegistry.js`: add the item to `MENU_ITEMS` (key, route, icon, `labelKey`, optional `badge`) / `OVERVIEW_CARDS` (key, `titleKey`, group and span) / `PAGES` (key, `titleKey`, `subtitleKey`); the texts go in `adminText.js` (ES and EN). The menu and the editor read the registry, so nothing else is needed for the menu.
2. **Backend registry** `backend/admin_ui_settings.py`: add the same key to `MENU_KEYS` / `OVERVIEW_KEYS` / `PAGE_KEYS` (the server refuses any key it does not know).
3. **The place that shows it**: a page uses `<PageHeader pageKey="the-key" ... />`; an Overview card draws its title with `<Editable keyPath="overview:the-key" ... />` and is placed by `overviewBlocks` (`src/admin/uiSettings.js`).
4. Tests: `src/admin/uiSettings.test.js` (the original menu must stay equal) and `backend/test_admin_ui_settings.py`.

An area added later appears at the end of the menu for studios that already saved a configuration, with its original name.

## Editing on the panel itself (inline)

"Personalizar panel" turns the real panel into an editor (`EditModeProvider`, only for the main admin): the words get a dashed outline and a pencil, a click (or Enter) opens a small field (limit and counter, Enter or leaving it keeps the text, Esc cancels, empty puts the original back, "Repor" appears on a customised text), the menu items and the Overview cards get a drag handle, up / down buttons and an eye (hidden ones stay, dimmed, while editing; the protected ones show a lock), and a bar at the bottom offers Save, Cancel, "Reset everything" (asks first) and a link to the advanced editor with tabs. A click on a menu item still navigates, so the draft is kept while moving between pages; leaving the admin (the site, logout) or cancelling with unsaved changes asks first. The draft lives only in memory (the same one the advanced editor uses) and nothing is saved until Save; a 409 says someone changed the panel meanwhile and offers to load the latest, and a refused text is shown next to its field and in the bar, in ES / EN. Outside edit mode (and for anyone who is not the main admin) `<Editable>` draws exactly the original element and nothing else.

### Making a new text editable (Phase 2)

1. Add the text to the registry `src/admin/uiRegistry.js`: it comes from `MENU_ITEMS`, `OVERVIEW_CARDS` or `PAGES` (and so from `EDITABLE_TEXTS`, which lists every editable text with its `path`, original text and limit). A new KIND of text needs a new path form in `parseKeyPath` / `textOfPath` / `setDraftText` (`src/admin/uiSettings.js`) and the same key in `backend/admin_ui_settings.py`.
2. Where the text is drawn, replace it with `<Editable as="h2" keyPath="overview:week" defaultText={t('week_title')} className="..." />` (`as` is the element that was there, so nothing changes outside edit mode). For a stat card use `<StatCard editKey="overview:..." />`; for a page title and subtitle just pass `pageKey` to `<PageHeader>`.
3. Overview cards get their controls from `<CardFrame>` (only drawn while editing) and the menu from `SidebarNav`; the logic of every change (reorder, rename, hide, protections, saving) is in `uiSettings.js` and is tested in `uiSettings.test.js`.

## Blocks: moving and hiding whole parts of a page

In edit mode (and in the advanced editor, tab "Blocks") the studio can move whole BLOCKS of a page up or down and hide the ones it does not use; never fields, table rows or the content of a block. A block moves only inside its own group of its page, a protected block (padlock) can be moved but never hidden, a page always keeps at least one visible block, and hiding only takes a block out of sight (its data and functions stay). It is saved in the same JSON under `blocks`: `{ "<page>": { "<group>": [{ "key", "hidden"? }] } }` (only the groups that differ from the original are sent); a key that no longer exists is ignored in silence, a block that is not saved yet appears last, and with no configuration the page is exactly the original. The server validates it with the same closed list (unknown page, group or block; a block in another group; repeats; a protected block hidden; a page without a visible block), the whole JSON may be 32 KB, and the version check (409) is unchanged. "Reset page" (in the edit bar and in the Blocks tab) puts the blocks of one page back as they were.

| Page (group) | Blocks, in the original order (protected ones marked 🔒) |
|---|---|
| Overview (`business`) | `biz_stats`, `biz_ending`, `biz_trainer`, `biz_nopack` (laid out in rows of 5 columns: 5, 3 + 2, 5) |
| Packs (`plans` / `main`) | `on_sale` 🔒, `archived`, `trial_prices` |
| Calendar (`calendar` / `main`) | `filters`, `legend`, `calendar` 🔒 |
| Trainers (`trainers` / `main`) | `note`, `access` 🔒, `list` 🔒 |
| Schedule (`schedule` / `main`) | `tabs` 🔒, `trainer_filter`, `list` 🔒 |

### Registering a new block (and marking it protected)

1. `src/admin/uiRegistry.js`: add `{ key, labelKey, protected?: true, span? }` to `BLOCKS[page][group]` in the ORIGINAL order (a new page or group is a new entry); the name goes in `adminText.js` (`blk_...`, ES and EN). `span` (of 5 columns) only matters for the groups listed in `GRID_GROUPS`. `protected: true` is what makes a block unhideable (padlock).
2. `backend/admin_ui_settings.py`: add the same key to `BLOCK_GROUPS[page][group]` and, if protected, to `PROTECTED_BLOCKS[page]` (the server refuses anything it does not know).
3. In the page, draw the blocks with `<BlockGroup pageKey groupKey gap blocks={{ key: (className) => <Element className={className} /> }} />`: each block is a function that receives the margin or column span it needs where it is (put it on its root element), or `null` when there is nothing to draw. `gap` is the margin given to every block but the first, so blocks keep no margin of their own on that side and can swap places.
4. Tests: `src/admin/uiSettings.test.js` (original order, protections, groups) and `backend/test_admin_ui_settings.py`.

## Texts inside the pages

Besides the menu, the Overview cards and the page titles, the studio can rename the words INSIDE the pages: section titles, table headers, filter and tab labels, main buttons and empty-list messages. It is a closed list (`src/admin/uiTexts.js`, mirrored by `backend/admin_ui_texts.py`), each text is `"<page>.<element>"`, up to 40 characters (60 for an empty-list message), saved in the same JSON under `texts` (`{ "texts": { "requests.approve": "Aceptar" } }`): one name for Spanish and English, empty = the original, a key that no longer exists is ignored in silence, and an older configuration (without `texts`) keeps working. In edit mode a click on the word (also on a button or a tab: it edits instead of acting) opens the field; the advanced editor has a "Texts" tab with every text grouped by page, a search by word, "Reset" for one text and "Reset page" for all the texts, the blocks, the title and the subtitle of a page. A button that deletes, cancels or approves only changes its text, never its function, and every confirmation dialog keeps its original text.

**What enters:** presentation words only. **What never enters** (a test checks it): error and validation messages, the status badges and state words (Pending, Booked, Cancelled, sent / failed...), anything the code compares or uses in logic, values that come from the database, technical placeholders and accessibility labels, the texts of confirmation dialogs and toasts, the subjects and bodies of the e-mails to clients, legal text, and anything that appears in ES / EN to the final client. The windows over a page (approve, new pack, new trainer...) and the calendar library's own toolbar are left for a later phase.

### Adding a new editable text

1. Add the page area / element to the page code with `<Txt id="<page>.<element>" />` in place of the plain `{t('key')}` (it draws the text and nothing else outside edit mode; for a prop that the component draws as a child, such as `title`, `label` or `hint`, pass the element: `title={<Txt id="..." />}`). Do not use it for `aria-label`, `placeholder`, `title="..."` attributes or text that is used as a string.
2. Register it in BOTH lists with the same key and limit: `src/admin/uiTexts.js` (`{ key, page, defaultKey, max }`; `defaultKey` is the original in `adminText.js`, ES and EN) and `backend/admin_ui_texts.py` (`TEXT_LIMITS`). The original must fit its limit in both languages, and an empty-list message is the only kind that may have 60.
3. Tests: `src/admin/uiSettings.test.js` fails if a `<Txt id>` is not registered, if a registered text is not drawn anywhere, if an original is longer than its limit, or if something that must never be editable gets in; `backend/test_admin_ui_settings.py` fails if the two lists differ.
